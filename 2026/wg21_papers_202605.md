### [P3377R0 constexpr `reinterpret_cast` partial replacements](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p3377r0.html)

定数式で使用可能な`reinterpret_cast`の代替機能の提案。

`reinterpret_cast`は定数式での使用が一切認められておらず、それによって`std::function`や`std::any`などの型消去を伴うようなライブラリ型を`constexpr`対応させることが妨げられています。

`reinterpret_cast`が定数式で使用できないのは、容易に未定義動作を踏む可能性があり（間違って使用しても意図しないフォールバックによって動作してしまう）、かつその汎用性が高すぎる（担っている機能が多数集積している）ことで、定数式においてポインタの安全な利用を保証することが困難になるためです。

この提案では、現在`reinterpret_cast`が担っている役割をユースケースごとに分離し、ユースケースごとに個別の定数式で使用可能な専用キャスト機能を追加することで定数式でも安全に`reinterpret_cast`の必要な機能を使用できるようにしようとしています。

この提案によるユースケース分類と、対応する機能を提案するかどうかは次のようになります

| 機能 | 提案 |
|---|---|
|ポインタ型と整数型の相互変換| しない |
|ポインタのタギング| P3125（C++26） |
|包含する型のポインタへのキャスト| する |
|オブジェクトのバイト列へのアクセス| しない |
|浮動小数点数ビット列の読み替え| `std::bit_cast` |
|整数ポインタの変換| しない |
|バイト配列をストレージとして利用する| する |
|バイト配列内オブジェクトのコピー| する |
|関数とオブジェクトのポインタ変換| しない |
|関数ポインタの型消去| する |
|メンバ変数ポインタの型消去| する |
|メンバ関数ポインタの型消去| する |

#### ポインタ型と整数型の相互変換

これは、ポインタ値を整数型に変換し、またその逆変換を行うことです。

```cpp
intptr_t iptr = reinterpret_cast<intptr_t>(ptr);  // 整数値への変換
auto * optr = reinterpret_cast<pointer>(iptr);    // ポインタ値へ戻す
```

これは

- ポインタのタギング
- 整数を引数に取る低レベルインターフェースへのポインタ受け渡し
- オブジェクトのサイズやアラインメントを意図的に無視するポインタ演算

などの用途があります。

ARM64eのポインタ認証や、C++定数評価機のようにアドレスが整数値のセマンティクスを持たないような場合に正しく動作させることが困難です。

この提案ではこれを可能にすることは提案していません。

#### ポインタのタギング

これは、ポインタの未使用ビットをタグとして利用することです。基本的に整数値に戻してビット演算などによってタグを埋め込むため、前項のアドレスと整数値の変換のユースケースの一部です。

これはC++26においてP3125の`std::tagged_pointer`によって定数式でも可能になっています。

```cpp
auto tptr = std::tagged_pointer<int, bool, 1>(&value); // tag is bool and we need only one bit

bool has_tag = tptr.tag(); // it's already bool
int * iptr = tptr.pointer(); // it's already correct pointer

assert(iptr == &value);
```

#### 包含する型のポインタへのキャスト

これは、標準レイアウト型においてメンバポインタからそのメンバが属するクラスのポインタへ変換することです。

```cpp
struct outer_t { int first; int second; };

outer_t outer{1,2};
auto * out1 = reinterpret_cast<outer_t *>(&outer.first);
auto * out2 = reinterpret_cast<outer_t *>(&outer.second); // ub
```

標準レイアウト型であれば共通初期シーケンス（common initial sequence）に一致する部分のポインタ変換を安全に行うことができます。`out2`の場合は共通初期シーケンスのポインタではないのでUBとなります。

この提案では`std::enclosing_cast`としてこのユースケース用のキャスト関数を提案しています。

```cpp
struct outer_t { int first; int second; };

outer_t outer{1,2};
auto & out1 = std::enclosing_cast<&outer_t::first_member>(outer.first);   // ok
auto & out2 = std::enclosing_cast<&outer_t::second_member>(outer.second);	// ok
```

#### オブジェクトのバイト列へのアクセス

これは、オブジェクトの領域を`std::byte`配列としてアクセスするためにポインタを`std::byte*`へキャストすることです。

```cpp
auto * bytes = reinterpret_cast<std::byte *>(obj);
```

ポインタを`std::byte*`に変換して読み出すことは（配列外参照が無い限り）合法であり、このキャストは問題ありません。

このユースケースのためのものは提案していません。

#### 浮動小数点数ビット列の読み替え

これは、浮動小数点数型のポインタを整数型ポインタにキャストしてアクセスすることで浮動小数点数のビット表現を取得しようとするものです。

```cpp
double pi = 3.14;
auto bits_of_pi = reinterpret_cast<int64_t>(pi);  // このキャストはUB
memcpy(bits_of_pi, pi, sizeof(pi)); // this is not UB
```

これはもろにstrict aliasing rulesに触れるためキャストからUBです。

このようなユースケースはC++20の`std::bit_cast`を使用することで安全に（定数式でも）利用可能です。

```cpp
double pi = 3.14;
auto bits_of_pi = std::bit_cast<uint64_t>(pi);
```

#### 整数ポインタの変換

これは整数型のポインタを符号の異なる整数型のポインタへキャストすることです。

```cpp
int * iptr = ...;
auto * uptr = reinterpret_cast<unsigned *>(iptr);
```

このユースケースのためのものは提案していません。

#### バイト配列をストレージとして利用する

これは、バイト配列（`char`の配列）を別の型のオブジェクトのストレージとして利用しようとするときのキャストです。

```cpp
char storage[N];
new(&storage[0]) T (...);
T * ptr = reinterpret_cast<T *>(&storage[0]); // 有効なポインタではない
```

このようなことを安全に行うには配置`new`の戻り値のポインタを保持しておく必要があります。

```cpp
std::array<char, N> storage;
new(storage.data()) T(...);   // ok
T & ref = std::object_cast<T>(storage.data());  // ok
```

この提案では、`std::object_cast`としてこのようなキャストをサポートしようとしています。

#### バイト配列内オブジェクトのコピー

これは、コピーしてきたバイト配列をオブジェクト表現として利用して新しいオブジェクトの生存期間を開始することです。

```cpp
memcpy(other_storage, storage, N);
T * first = std::start_lifetime_as<T>(&other_storage[0]); // 定数式で使用できない
T * rest = reinterpret_cast<T*>(&other_storage[0]); // UB
```
```cpp
std::array other_storage = storage; // trivially copyable T
T & all = std::object_cast<T>(other_storage.data());
```

提案では、`std::object_cast`でこのようなユースケースをサポートしようとしています。

#### 関数とオブジェクトのポインタ変換

これは、関数ポインタをオブジェクトポインタにキャストして、それを元に戻すことです。

```cpp
auto * optr = reinterpret_cast<T *>(fptr); // yes, really
auto * fptr = reinterpret_cast<int(*)()>(optr);
```

このようなキャストはポインタのサイズが合う限りは条件付きでサポートされているようで、`void*`を受け取るインターフェースにコールバックを渡す際などに使用されることがあるようです。

標準ライブラリの機能を定数式対応させるためには不要なので、このユースケースのためのものは提案していません。

#### 関数ポインタの型消去

これは、関数ポインタを`void(*)()`のようなポインタに型消去してから元に戻すキャストの事です。

```cpp
auto * erased = reinterpret_cast<void(*)()>(fptr);
int(*fptr)() = reinterpret_cast<int(*)()>(erased);
```

型消去したポインタを用いて関数呼び出しを行わない限りはUBにならないようです。関数ポインタを受け取るインターフェースに対して型が合わな関数を渡すために使用されることがあるようです。

```cpp
auto erased = std::a_function_pointer{fptr};

auto fptr = function_pointer_cast<int()>(erased);
auto fptr = static_cast<int(*)>(erased); // alt
```

この提案では、`a_function_pointer`と`function_pointer_cast`でこのようなユースケースをサポートしようとしています。

#### メンバ変数ポインタの型消去

これは、メンバ変数ポインタを空のクラスのメンバポインタにキャストして元に戻すことです。

```cpp
struct empty_t {}; // yes you can do a member pointer of this
auto * erased = reinterpret_cast<int (empty_t::*)>(mdptr);
auto mdptr = reinterpret_cast<float (my_type::*)>(erased);
```
```cpp
auto erased = std::a_member_data_pointer{mdptr};

auto mdptr = member_pointer_cast<float (my_type::*)>(erased);
auto mdptr = static_cast<float (my_type::*)>(erased); // alt
```

この提案では、`a_member_data_pointer`と`member_pointer_cast`でこのようなユースケースをサポートしようとしています。

#### メンバ関数ポインタの型消去

これは、一つ前のユースケースのメンバ関数ポインタ版です。

```cpp
struct empty_t {}; // yes you can do a member pointer of this
auto * erased = reinterpret_cast<void (empty_t::*)()>(mfptr);
auto mfptr = reinterpret_cast<int (my_type::*)(float)>(erased);
```
```cpp
auto erased = std::a_member_function_pointer{mptr};

auto mfptr = member_pointer_cast<int (my_type::*)(float)>(erased);
auto mfptr = static_cast<int (my_type::*)(float)>(erased); // alt
```

この提案では、`a_member_function_pointer`と`member_pointer_cast`でこのようなユースケースをサポートしようとしています。

メンバ変数ポインタとメンバ関数ポインタを区別して扱っているのは、メンバ変数ポインタとメンバ変数ポインタでそのサイズが異なる場合があるためです。


`a_function_pointer`、`a_member_data_pointer`、`a_member_function_pointer`は上記例ではキャスト関数のように使用されていますが、ポインタの値を保持するために領域が必要になるため、その実態はクラス型です。提案ではライブラリ型としてこれらの機能を提案していますが、言語機能としてこれらの型を提供することで汎用的なコードでの取り扱いが簡単になる可能性があります。

この提案の主目的は定数式で`reinterpret_cast`相当の機能を使用可能にすることにありますが、ここで提案されている機能は定数式専用ではなく実行時にも使用可能にすることを意図しています。これによって、現在`reinterpret_cast`を使用していることで何がしたいのかが不明瞭になっているコードでも、よりユースケースに特化したこの提案による機能を使用することでコードの意図が明確になります。

### [P3850R0 A proposed plan for extending Contracts in C++29](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p3850r0.pdf)

C++29に向けたContracts機能の拡張計画提案。

C++26のContracts機能は当初からそれで完成するものではなく、MVP（minimal viable product）としてまず最初の最小機能を導入したものです。そのため、C++29以降でその機能の拡張が予定されており、この文書は現段階でのそのロードマップを示したものです。

C++29に向けての目標はC++26の策定期間（特に終盤）に提起された問題や機能不足の指摘になるべく対処することであり、C++26 Contractsの設計意図や機能を維持しながらもそれらの懸念への対処を優先するとしています。

とはいえ懸念の全てや求められる機能拡張の全てを導入する事はできず、実装負荷も考慮に入れる必要があります。そこで、次の基準を設けてこれをなるべく多く満たすものを優先することを提案しています

- A. 価値: 多様なC++ユーザーに大きな価値をもたらすもの
- B. 緊急性: C++26サイクルで提起された重要な懸念への対処
- C. 成熟度: 提案の設計が完了しており、EWG/LEWGのレビュー準備が整っている
- D. レビュー: WG21のサブグループで1回以上のレビューを受けており、フィードバックが反映されている
- E. 仕様: 完全な文言が用意されており、仕様に関する未解決の疑問点がない
- F. 実装: 主要なコンパイラにおいて、少なくとも1つの完全かつ動作する実装が存在する

この基準に照らして現時点でC++29に向けて作業していく優先目標として選択されたのは次の6つです

|提案|機能|基準|大きさ|
|---|---|---|---|

| P3290R4 | 違反ハンドラの手動呼び出し | ABCDE | 小 |
| P3400R3 | ラベル | ABCD | 大 |
| P3100R6 | 暗黙の契約アサーション | ACDE | 大 |
| P3098R2 | 事後条件のキャプチャ | ACD | 中 |

### [P4013R0 constexpr `any` of all the things](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4013r0.html)

`std::any`を`constexpr`にする提案。

単に値をあちこちに渡すだけでその値に対して操作を行わないというケースがあります。その場合C++ではテンプレートやポリモーフィズムの利用、`void*`などの選択肢があります。これらの選択肢にはそれぞれメリットとデメリットがありますが、C++26ではいずれの方法も定数式で使用可能です。

その選択肢の一つとして`std::any`があり、これを使用すると任意の型の値を渡していることが明確になり、その所有権について意識する必要がないなどのメリットがあるものの、これは定数式で使用可能ではありません。

単に定数式で使用可能ではないという理由だけで`std::any`を使用する選択肢を妨げないようにするために、`std::any`を`constexpr`させようとするのがこの提案です。

`std::any`の実装は内部的に型消去のためのメタデータ型を持っており、メタデータ型にコンストラクタ等で渡された値を乗せて、メタデータ型オブジェクトを基底クラスの仮想関数経由で扱うことで`std::any`のレイヤでは型情報を保持しないようにしています。メタデータ型の選択時には乗せる型の性質やSSOの可否によって条件分岐が行われます。

この提案では、この条件分岐の一番最初に`if consteval`による分岐をおいて、定数式においては常にメモリ確保によってメタデータ型オブジェクトを保持するようにすることで実装することを提案しています。こうすることで、現在の実装を大きく変更することなく、`std::any`を容易に定数式で使用可能にできます。そして、これを行うための言語的な障壁は無いため、標準の作業としては`std::any`のメンバ関数等に`constexpr`を付加するだけです。

I/Oの観点から、バイト列を表現するベストな型を考察する文書。

バイトシーケンスを表す型としては`std::span<std::byte>`が一番に上がりますが、この文書ではI/O処理においてはそれだと使いづらい面があり、専用のバッファ型が必要になる事を説明しています。

`span<byte>`では不十分な理由は、プラットフォームで定義されるI/O操作が多くの場合1つのバイトバッファ（領域）を取るのではなくバイト領域の配列を取るようになっているためです。これにより、`span<byte>`はI/Oのためのバッファを表現するのに不十分となります。

`span<span<byte>>`ならばバッファ配列を表現することができます。しかし、バッファそのもの（`span<byte>`）はどこかに実体を持ちそれを借用するだけだったとしても、そのビューの配列（`span<span<byte>>`）が必ずしもそうであるとは限りません。バッファ配列そのものの所有権はどこか別の場所にあるものではなく、そうしないと関数の呼び出し境界で`span<span<byte>>`を返す事で容易にダングリングしてしまいます。

```cpp
class message {
  span<span<byte>> buffers_; // borrows... what?
};

span<span<byte>> prepare_message(span<byte> hdr, span<byte> body) {
  span<byte> bufs[] = { hdr, body };
  return { bufs }; // dangling
}

void start_send(socket& s, span<byte> hdr, span<byte> body) {
  span<byte> bufs[] = { hdr, body };
  s.async_send(span<span<byte>>(bufs), callback);
  // returns immediately; bufs destroyed; dangling
}
```

`vector<span<byte>>`のように`span<byte>`の`range`にすればこの問題を解消することができます。この場合は、バッファ配列全体を1つのバッファとして扱ってバッファの消費を表現することができません。`vector<span<byte>>`に対してRangeアダプタを適用しても、バッファ単位の操作になりバイト要素単位ではありません。バッファ配列という構造を維持したままバッファの消費という操作を行う方法が無いため、この表現は適していません（`views::join`はバッファ配列という構造が維持されないので選択肢に上がらない）。

そのような操作が追加されたとしても、`std::span<byte>`がすでにバイト配列のビューとして使用されすぎているために、I/O専用のバッファ操作アルゴリズム（Rangeアダプタ）は`std::span<byte>`によって表現されているものがI/Oバッファなのかそれ以外のもの（シリアライズ・暗号化・ハッシュ・メモリマップなど）を区別できません。これにより、I/Oバッファ専用のデバッグなどを組み込むことが難しくなり、安全性が損なわれます（`BOOST_ASIO_ENABLE_BUFFER_DEBUGGING`のようなもの）。

この文書では、Boost.Asioの`mutable_buffer`（書き込み可能バッファ）/`const_buffer`（読み込み専用バッファ）がI/Oのためのバッファとして適しているとしています。

```cpp
class mutable_buffer {
  unsigned char* p_ = nullptr;
  std::size_t n_ = 0;
public:
  mutable_buffer() = default;
  mutable_buffer(mutable_buffer const&) = default;
  mutable_buffer& operator=(mutable_buffer const&) = default;
  constexpr mutable_buffer(void* data, std::size_t size) noexcept
      : p_(static_cast<unsigned char*>(data)), n_(size) { }
  constexpr void* data() const noexcept { return p_; }
  constexpr std::size_t size() const noexcept { return n_; }
  constexpr mutable_buffer& operator+=(std::size_t n) noexcept
      { p_ += n; n_ -= n; return *this; }
};

class const_buffer {
  unsigned char const* p_ = nullptr;
  std::size_t n_ = 0;
public:
  const_buffer() = default;
  const_buffer(const_buffer const&) = default;
  const_buffer& operator=(const_buffer const& other) = default;
  constexpr const_buffer(void const* data, std::size_t size) noexcept
      : p_(static_cast<unsigned char const*>(data)), n_(size) { }
  constexpr const_buffer(mutable_buffer const& b) noexcept
      : p_(static_cast<unsigned char const*>(b.data())), n_(b.size()) { }
  constexpr void const* data() const noexcept { return p_; }
  constexpr std::size_t size() const noexcept { return n_; }
};
```

これはNetoworking TSにすでにあるものです。

これらは`span<byte>`に対応するバッファ型であり、バッファ配列型ではありません。バッファ配列型はこれらの`range`（`vector<mutable_buffer>`など）で表現するようにしています。`mutable_buffer`が要素単位の操作をサポートしていることと、バッファ型が`span<byte>`ではないことでI/Oバッファ配列専用のアルゴリズムを提供可能になり、前述の問題が解消されるためです。

I/Oやネットワークに`std::execution`を使用した場合のコストについて分析する文書。

この文書は、コルーチンI/O（P4100 Network Endeavor）によるコルーチンネイティブI/Oと`std::execution`によるI/Oのコストを比較し、`std::execution`によるI/Oでは避けられないオーバーヘッドが存在する事を説明した文書です。

この文書では、`execution::task`について現時点で知られている修正が全て適用されたと仮定して、次の2つのものを比較しています

- I/O操作は`awaitable`を返す
    - コルーチンネイティブケース: `io::task<T>`を使用する
- I/O操作は`sender`を返す
    - ケースA: `execution::task<T, IoEnv>` + I/O Awaitable
        - 個々のI/O操作は`awaitable`を返すが、タスク管理は`execution::task`を使用する
    - ケースB: `execution::task<T, IoEnv>` + I/O Sender
        - 現在の方向性、I/O操作もすべて`execution::task`を使用する

いずれのケースでもユーザーコードの見た目は同様で次のようになります

```cpp
TASK session(tcp_socket& sock) {
  char buf[1024];

  auto [ec, n] = co_await sock.read_some(
      mutable_buffer(buf, sizeof buf));

  if (ec)
      co_return;

  co_await process(buf, n);
}
```

戻り値型の`TASK`が異なり、上記3つのケースごとに変化します。また、`sock.read_some()`が`sender`を返すか`awaitable`を返すかも異なります。

動作の違いは主に`co_await`の処理方法にあり、`sender`を返す場合（ケースB）は`affine`の呼び出しやその`sender`に対する`connect`=>`start`およびそれらをコルーチンにアダプトするラッパーが必要になります。一方コルーチンネイティブケースとケースAでは直接コルーチンの仕組みによって処理されます。ケースAとケースBの違いは`sock.read_some()`がそのコストを負担するかが異なり、ケースAの場合はそのようなコストが発生するのは`process()`のみです。

詳細は割愛して、各ケースの異なる点をまとめたのが次の表です

| Property | コルーチンネイティブ | ケースA | ケースB |
| :--- | :--- | :--- | :--- |
| テンプレートパラメータ数 | 1 | 2 | 2 |
| タスクごとの`sender`コンセプトインスタンス化 | 0 | チェーン内のタスク型ごとに 1 | チェーン内のタスク型ごとに 1 |
| タスク間`co_await`中断時 | 2つのポインタ保存 | `state<Rcvr>`構築 + スケジューラ抽出 | `state<Rcvr>`構築 + スケジューラ抽出 |
| I/Oの`co_await`中断時 | 2つのポインタ保存 | 2つのポインタ保存 | `state<Rcvr>`構築 + スケジューラ抽出 |
| I/O`co_await`時の`affine`ラップ | 0 | 0 | I/O 操作ごとに1 |
| I/O`co_await`時対称転送 | あり | あり | なし (`set_value`が`void`を返すため) |
| 型消去ストリームI/Oでのメモリ確保 | 0 | 0 | I/O 操作ごとに1回 |

パフォーマンスにクリティカルなのは上2つを除いた部分です。ケースBは言わずもがな、ケースAでも`sender`/`receiver`プロトコルに起因するコストが発生します。

タスク間`co_await`中断とは、`task`のコルーチン内で`co_await child_task`のようにする場合に起こる主`task`の中断の事です。他の関連文書で説明されているように、I/O Awaitableはこの場合にフレームアロケータをカスタマイズし対称転送も行いながら中断する（コルーチンの仕組み内で中断と子タスク実行、再開を行う）ことができますが、`sender`モデルではコルーチンへのラップや子タスク（`sender`）の`start`などの追加の処理を行う必要があります。

ケースAの場合は`sock.read_some()`にはこのコストはかかりませんが、ケースBは2つの`co_await`でこのコストが発生します。

さらに、このようなコストはHTTPのなどのより具体的なI/Oに適用した際に個別のI/O操作によって増幅されることになります。

この文書による分析は実際の実装のベンチマークを取ったものではなく、実装上避けられない理論上のオーバーヘッドについて比較したものです。そのため、そのオーバーヘッドが実際にどの程度のコストになるのかは実行環境によります。ただ、オーバーヘッドのトリガーとなる避けられない操作（`sender`プロトコルの構築と破棄、操作呼び出しなど）が存在しておりコルーチンネイティブI/Oではそれは回避できる、ということを主張しています。

この文書の結論は、コルーチンネイティブI/Oを使用すれば回避可能なオーバーヘッドが`sender`を使用する場合に発生してしまうため、コルーチンネイティブな`task`型（`std::execution::task`に対して`std::io::task`が並立すること）を認めるべきというものです。ただし、文書としては何かを提案しておらず、あくまでそのような決定に必要な根拠を提示するものです。

### [P4124R0 Info: Combinators and Compound Results from I/O](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4124r0.pdf)

`when_all`を始めとする操作の成功やエラーを認識する`sender`アルゴリズムがI/Oの結果を扱えない問題の解決策に関する文書。

コルーチンI/O（P4100 Network Endeavor）の他の文書で何度か言及されているように、I/O操作の戻り値型は`(error_code, length)`の組であり、これが値チャネルを通じて返されることによって、`sender`/`receiver`の3チャネルに上手くフィットさせることができません。

この問題は特に、`when_all`や`retry`などのエラーチャネルの結果に反応するタイプの`sender`アルゴリズムにおいて問題になります。I/Oの結果は値チャネルで返されていることで、値チャネルで返されるエラーを扱うことができないためです。

`(error_code, length)`はBoost.Asioで確立されているソケット通信等の戻り値型ですが、I/Oの戻り値型は他のものもの考えられ、P4166R0のI/O操作の結果型である`io_result<Ts...>`型は、`std::tuple<std::error_code, Ts...>`のような結果型となっています。

例えば複数のI/O操作を受け取って実行し結果を`io_result<Ts...>`にまとめる`io::when_all(child1, child2, ..., childN) -> io_result<T1, T2, ..., Tn>`のようなものを考えることができます。

```cpp
auto [ec, n1, n2, n3] = co_await io::when_all(
    stream.read_some(buf1),
    stream.read_some(buf2),
    stream.read_some(buf3));
```

`io::when_all()`に与えられて子操作はすべて`io_result<Ts...>`を返すものとして、すべての操作がエラーを返さなければ`io::when_all()`の結果もエラーにならず、いずれか1つの操作ががエラーになった場合はそのエラー（`std::error_code`）を返して残りの操作はキャンセルされます。

`io::when_all()`はIoAwaitableプロトコル（`io_result<Ts...>`）を認識することでこのような動作が可能になっています。

この`io::when_all()`のようなものは`std::execution`にも`when_all`アルゴリズムとして存在しており、`sender`の3チャネルを監視することで同様の動作をします。値チャネルで完了した場合は正常終了として残りの子操作の待機を継続しますが、エラーチャネル/停止チャネルで完了した子操作がある場合は残りの子操作をキャンセルして最初に正常終了しなかった操作の結果を返します。

`execution::when_all`ではコルーチンを使用することもでき、`io_result<Ts...>`を返すコルーチン非同期I/O操作に対して`execution::when_all`を適用することもできます。

```cpp
co_await std::execution::when_all(
    sock.async_read_some(buf1),   // set_value(ec, n)
    sock.async_read_some(buf2));  // set_value(ec, n)
```

しかし、`io_result<Ts...>`を返す非同期操作は`sender`として扱われた時に値チャネルで結果（`std::error_code`+結果値）を返し、エラーチャネルには例外がが接続されます。このため値チャネルで正常終了値とエラー値が返されることになり、`execution::when_all`は`io_result<Ts...>`を返すコルーチンのエラーを認識することができなくなります。結果、`execution::when_all`ではいずれかの子操作でエラーが起きても他の操作はキャンセルされることなく、すべて完了するまで待機して（例外が無ければ）正常に完了してしまいます。

この文書ではこの問題の根本解決のためにドメイン認識コンビネーター（Domain-Aware Combinators）を提案しています。

これは、同じ`when_all()`という名前を使用するが、与えられた子操作（引数）に応じて処理を切り替えるものです。`io_result<Ts...>`（を返すコルーチン）が与えられた場合は先ほどの`io::when_all()`のようなコルーチンネイティブの実装にディスパッチし、`sender`が与えられた場合は`execution::when_all`にディスパッチします。

```cpp
// ドメイン認識when_allの使用例
auto [ec, n1, n2] = co_await when_all(
    sock.async_read_some(buf1),
    sock.async_read_some(buf2));

co_await when_all(
    gpu_task_a(),
    gpu_task_b());
```

これはコルーチンI/Oが導入された場合に必要になるものとして紹介されており、その場合には2つのドメイン（非同期モデル）を統合して扱いつつそのためのオーバーヘッドを最小にすることができます。

`sender`アルゴリズムの多くはコルーチンにおいても通常のC++の制御構文が対応していますが、`when_all()`を始めとする並行処理用のアルゴリズム（コンビネーター）はそのままだと対応するものがありません。コルーチンI/Oが導入される場合は`std::execution`のものを使用することになりますが、それには上記チャネル不一致の問題とそれを回避するためにかかるコストがあり、コルーチンに対応するものがないアルゴリズムについてはドメイン認識コンビネーターを導入することで利用者の負荷とコストを最小化することができます。

コルーチンフレーム用アロケータのカスタマイズ方法が実質的に2種類しかない事を説明した文書。

この文書はコルーチンI/O（P4100 Network Endeavor）の一部として、IOAwaitableプロトコルが採用するTLSを使用した伝播方法が数ある選択肢から選ばれた好みの設計選択ではなく、わずか2つの選択肢のうちの一つであることを解説するものです。

コルーチンである関数は、呼び出されるとコルーチンの初期化処理をコンパイラが行って、その後コルーチン内の最初の中断地点で処理を中断して呼び出し元に処理を返します。コルーチンの初期化処理内ではまずいの一番にコルーチンフレームのためのメモリ領域が確保され、HALOと呼ばれる最適化が適用されない場合これを回避することはできません。

コルーチンフレームの確保はコルーチン内のユーザーコードよりも、プロミス型の初期化よりも早く行われます。

```cpp
task<int> fetch(socket& s, buffer& b);

auto t = fetch(sock, buf);  // operator new HERE
co_await t;                 // too late
```

ただし、メモリ確保の方法をカスタマイズする手段が提供されていない訳では無く、プロミス型の文脈で発見可能な`operator new`を定義しておくことでコルーチンフレームのメモリ確保方法をカスタマイズすることができます。

`promise_type::operator new`にはフレームサイズとコルーチンに渡された引数列が渡されて（それらを渡すことのできる候補が探索されて使用されて）呼び出されるため、プロミス型における定義だけでなくコルーチンに与えた引数列によってもカスタマイズを行うことができます。

メモリの確保方法をより柔軟にカスタマイズできるようにするために、C++にはアロケータという仕組みがあります。コルーチンは直接的にアロケータをサポートしているわけではありませんが、`promise_type::operator new`に上手くアロケータを渡すことができればそこでアロケータを使用するようにすることでアロケータ対応をさせることはできます。

しかし、この`operator new`呼び出しがコルーチンの他のあらゆるカスタマイズポイントよりも早く実行されることで、コルーチンにアロケータを渡す方法は実質的に2つに絞られます。

1. コルーチン呼び出し時の引数リストで渡す
    - `allocator_arg_t`を使用する定型パターンで渡すことができる
2. 環境状態経由で渡す
    - グローバル変数やTLSなどの外部状態経由で渡すことができる

1の方法は明示的かつ分かりやすい代わりに、コルーチンの呼び出しチェーン全体でアロケータを明示的に引き渡す必要があり、関数シグネチャと呼び出しコードが汚染されます。

```cpp
task<int> fetch(std::allocator_arg_t,
                MyAllocator alloc,
                socket& s, buffer& b);
```

この`fetch()`コルーチン内で他の（HTTP I/Oなど）コルーチンを待機する場合、そのコルーチンの呼び出しにもこのアロケータを手動で伝播する必要があります。

2の方法は1のデメリットがなくアロケータのやり取りはすべて暗黙的に行われることになりますが、それそのものがデメリットとなります。また、グローバル状態だと粒度が粗すぎてプロセス内の全てのコルーチンのアロケータを同時に変更してしまうことになります。

IOAwaitableプロトコルでは2の方法かつTLSを使用したフレームアロケータの伝播を採用していることで、コルーチンユーザーはアロケータのカスタマイズが不要であればそれを気にすることなく使用でき、カスタマイズする場合でも呼び出し元でカスタマイズすれば手で引き回す必要はありません。

この文書ではこの設計選択について説明されています。

また、この2つの経路は排他的なものではなく、`promise_type::operator new`のオーバーロードによって共存させることができます。

```cpp
struct promise_type {
  // Path A: allocator_arg_t in parameter list
  template<typename Alloc, typename... Args>
  static void* operator new(std::size_t sz, std::allocator_arg_t, Alloc& a, Args&&...)
  {
    return allocate_frame(sz, a);
  }

  // Path A: member function variant
  template<typename T, typename Alloc, typename... Args>
  static void* operator new(std::size_t sz, T&, std::allocator_arg_t, Alloc& a, Args&&...)
  {
    return allocate_frame(sz, a);
  }

  // Path B: ambient state fallback
  static void* operator new(std::size_t sz)
  {
    auto* mr = get_cached_frame_allocator();
    if (!mr)
        mr = std::pmr::new_delete_resource();
    return allocate_frame(sz, mr);
  }
};
```

このようにしておくことで2つの経路を同居させることができ、ユーザーの選択によって適切な経路を利用してフレームアロケータのカスタマイズを行うことができます。IOAwaitableプロトコルでもこれが採用されています。

定数評価の外側に出る際に呼び出されるカスタイマイズポイントの提案。

定数式の結果の値はどこかで定数評価を抜けて実行時に参照可能な値になる場合があります。これは現在暗黙的に起こっており、これを検出する方法は基本的に存在しません（コンパイル時に確保したメモリを開放しないまま定数式を抜ける場合などエラーになる場合はあります）。この提案は、ある型の値が定数評価を抜ける場合に呼び出されるカスタイマイズポイントを導入することでこの瞬間の検知を行えるようにしようとするものです。

これによって、P3771R0で提案されているmutexの`constexpr`対応におけるデッドロック野定数式での検出をライブラリ機能のみで行えるようになるほか、コンパイル時`std::string`が定数式を脱出する時に`define_static_string`を呼ぶことで定数式での動的メモリを開放するようにするなどの処理が行えるようになります。

この提案のアプローチは、クラスの特定のメンバ関数をそのクラスの値が定数式から脱出する際に呼び出されるようにするものです。

```cpp
class mutex {
	...

  // 定数式からの脱出点におけるカスタマイズポイント
	consteval mutex & magic_function() const {
		if (this->__is_locked()) {
			throw __custom_error_message{"leaking locked mutex"};
		}
		return *this;
	}
}
```

`magic_function()`は仮名です。この例では`mutex`が`constexpr`対応している場合に、`mutex`値が定数式を抜ける際にロックを保持していないことを検出しています。

このカスタマイズポイントは定数式から脱出する際、その直前に呼ばれるため、そこはまだ定数評価の中です。そのため、`consteval`関数になっています。

`std::string`を固定配列に移動する例

```cpp
class string {
	// ...
	constexpr const char * data() const;
	constexpr size_t size() const;
	constexpr const_iterator begin() const;
	constexpr const_iterator end() const;
	
	consteval string magic_function() const {
		return {std::meta::define_static_string(*this), this->size()};
	}
	
	constexpr ~string() {
		if (!__is_static_storage(this->data())) { // assume we have such magical function
			delete[] this->data();
		}
	}
};
```

この関数が返す型を変化させることができれば、より汎用性が高まるかもしれません。

```cpp
template <typename T> class vector {
	// ...
	consteval auto magic_function() const {
		return define_static_array(...);
	}
}
```

このカスタマイズポイントは、ある関数が定数評価から静的ストレージ領域へ、あるいは実行時に使用可能な値へと移行する場合に、コンパイラは`consteval`なメンバまたはフリー関数を探索し呼び出すことによって機能します。呼び出される関数は対象のオブジェクトを右辺値で受け取り、その場で変更を行うか自信あるいは別の型を返してその位置に置き換えることができます。

```cpp
// constexpr変数
constexpr auto a =                constant_calculation();  // before
constexpr auto b = magic_function(constant_calculation()); // after (implicitly)
```
```cpp
// static constinit変数
static constinit auto a =                constant_calculation();  // before
static constinit auto b = magic_function(constant_calculation()); // after (implicitly)
```
```cpp
// consteval評価
consteval auto constant_calculation() { ... }
	
auto function() { // notice it's not constexpr nor consteval
	auto a =                constant_calculation();  // before
	auto b = magic_function(constant_calculation()); // after (implicitly)
}
```

この提案では、対象の関数についてフリー関数とメンバ関数の両方を考慮するようにすることを提案しています。これは、メンバ関数だけだと非侵入的に型の拡張を行えないためです。

このカスタマイズポイントが呼び出されるより具体的なタイミングについては次の2つ選択肢を提示しています

1. 定数評価によって値が生成される度に
    - つまり、常に呼び出される
2. 定数評価の外部でその値がODR使用される時
    - 使用時にしか呼び出されない

1つ目の方法のメリットは実装が容易なことです。2つ目の方法のメリットは、常には処理されず、実行時に使用される場合にのみ処理されることです（コンパイル負荷が低い）。

### [P4166R0 Info: Benefits of Frame-Visible Coroutines for Senders](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4166r0.pdf)

フレーム可視なコルーチンについて解説した文書。

フレーム可視なコルーチン（Frame-Visible Coroutines）とは、C++20で追加されたスタックレスコルーチンにおいてコルーチンフレームの特性（レイアウト、サイズなど）が不透明になっているのに対して、コルーチンフレームのレイアウト等を可視にするものです。

コルーチンフレームは`std::coroutine_handle<>`の背後に隠されており、コルーチン利用側からはそのレイアウト等が全く開示されていません。これはコルーチンフレームのサイズをコルーチンそのものの最適化の後で決定するための性質ですが、これによってコルーチンではコルーチンフレームのヒープへの確保が基本的に必要になっており、コルーチン境界を越えた最適化も阻害されています。

`sender`/`receiver`プロトコルからコルーチンを利用する際（`execution::task`など）においてもコルーチンラップのためのヒープ確保が避けられなくなっています。

もしフレーム可視なコルーチンが導入されると、`execution::task`などの`sender`とコルーチン結節点におけるヒープ確保が不要になり、コルーチン利用側からコルーチン境界の先が可視になることによって更なる最適化も可能になります。

そして、フレーム可視なコルーチンはコルーチンそのものにとっても同様のメリットをもたらします。

フレーム可視なコルーチンが導入された場合の各モデル（コルーチン/`sender`）が受けるメリットのまとめ

| 機能・性質 | C++20コルーチン | フレーム可視なコルーチン | `sender` |
| :--- | :---: | :---: | :---: |
| 最適化器からの可視性 | なし | **あり** | **あり** |
| ゼロアロケーションの合成 | なし | **あり** | **あり** |
| コンパイル時ワークグラフ記述 | なし | なし | あり |
| 言語の制御構文 (`for`,`if`等) | 使用可能 | 使用可能 | 使用不可 |
| 複合結果の完全保持 | 可能 | 可能 | できない場合がある |

コルーチンベースの`sender`アルゴリズムをフレーム可視なコルーチンで構成する場合、`sender`の列はコルーチンに対して欠けている特性（言語の制御構文の使用と複合結果の完全保持）を手に入れることができます。

C++20コルーチン（フレーム不透明）にもその型消去特性そのものによる恩恵（型消去ストリームの実装やABI安定性、分離コンパイルなど）があるため、不要になるわけではありません。

一方で、コンパイル時ワークグラフ記述は`sender`の独自の特性であり続けます。

### [P4189R0 get()ing the pointer from optional](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4189r0.html)

`std::optional`から内包する要素へのポインタを取得する関数を追加する提案。

無効値を取りうる値を表現するために、Cや古いC++のAPIでは`std::optional`ではなくポインタが使用されます。このようなライブラリとの接続部においては、`std::optional`をポインタに変換するための簡易な方法がありません。

また、C++26で追加された`std::inplace_vector`の`.try_*_back()`関数（要素の追加を試みる）は、最終的に戻り値型がポインタから`std::optional<T&>`に変更されましたが、その際の反対意見の一つとして`std::optional<T&>`を`T*`に変換する簡易な方法が無いというものがありました。おそらく、`std::inplace_vector`が使用されるような領域では`std::optional`の代わりにポインタを取るインターフェースが採用されている場合がより多くなるためだと思われます。

`std::inplace_vector`において`.try_*_back()`関数から結果のポインタへの変換をワンライナーで書こうとすると例えば次ようになります

```cpp
iv.try_emplace_back(/* ... */).transform([](auto& r) { return std::addressof(r); }).value_or(nullptr);
```

他の書き方もありますが、いずれにしても戻り値型変更前のように簡潔にはなりません。

また、C++26のNBコメントにもこの点を指摘するものがあるようです。

この提案は、このような需要に対応して`std::optional`に`.get_ptr()`メンバ関数を追加することを提案するものです。`std::optional<T>`と`std::optional<T&>`の両方に対して追加することを提案しています。

```cpp
template<typename T>
class optional {
  ...

  constexpr T* get_ptr() noexcept;
  constexpr const T* get_ptr() const noexcept;

  ...
};
```

`.get_ptr()`メンバ関数は、有効値を保持している場合はその値へのポインタを、無効値を保持している場合は`nullptr`を返します。

これを用いると先ほどの`std::inplace_vector`の例は次のように書けるようになります

```cpp
iv.try_emplace_back(/* ... */).get_ptr();
```

`.get_ptr()`という名前および設計はBoost.Optionalにおける先例を踏襲しています。

### [P4198R0 Runtime Indexed Tuples](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4198r0.pdf)

実行時にインデックス指定アクセス可能な`tuple`型の提案。

`std::tuple`の要素へアクセスするためにはコンパイル時にインデックスまたは型を指定してアクセスする必要があり、実行時に動的に要素を指定することはできません。実行時インデックスを用いて`std::tuple`の要素へアクセスするには`std::tuple<Ts...>`に対して`std::variant<Ts...>`を返す`switch`文を記述する必要があります。

```cpp
template<typename... T> 
std::variant<T...> Get_at_index(std::tuple<T...> list, std::size_t index) { 
  switch (index) { 
    case 0: return std::get<0>(list); 
    case 1: return std::get<1>(list); 
    // ... scales poorly for large packs 
  } 
} 
```

この方法は要素数`N`に対して最悪の時間計算量が`O(N)`になります。

この提案は実行時インデックスによって効率的にアクセス可能な新しい`tuple`型、`std::runtime_indexed_tuple`を提案するものです。提案の目的は、実行時インデックスでアクセスできてなおかつそれが効率的（`O(1)`）である`tuple`型を導入することにあり、既存の`std::tuple`ではABI互換性の縛りからそれが不可能とのことです。

`std::runtime_indexed_tuple`のイメージ

```cpp
template<typename... T> 
struct runtime_indexed_tuple<T...> { 
  // Requirements: The same as ordinary tuples 

  auto operator[](std::size_t index) -> std::variant<T&...>;
}; 
```

`std::variant`は参照型を保持できないため、この提案ではこのために`std::variant<T&...>`を導入しようとしています。この`std::variant<T&...>`は

- 値を持たない状態にならない
- 一度参照で初期化したら型を切り替えられない
- 代入は`std::variant<T&...>`を書きかえるのではなく、参照先への代入になる

などの特性を持ちます。

さらに、この`std::variant<T&...>`から指定した`T&`を取り出すための`std::optional<T&>`への変換も提案しています。

提案文書より、サンプルコード

```cpp
int main() {
  // 使用法はstd::tupleと同じ
  std::runtime_indexed_tuples<int, double, float, int> list{ 1, 2.0, 3.0f,3 }; 

  // 要素アクセス
  std::cout << *std::get<2>(list[0]) << std::endl; 
  std::cout << *std::get<0>(list[1]) << std::endl; 
  std::cout << *std::get<1>(list[2]) << std::endl;

  return 0; 
}
```

`std::get`はおそらく`std::optional<T&>`を返します。`std::get<N>`の`N`の順序が入れ替わっているのは実装の都合の様ですが、`std::visit`を用いて扱えばいいのでこれは問題にならないとしています。

提案には、この`std::runtime_indexed_tuples`の効率的にアクセス可能な実装の例が記載されています。

### [P4205R0 Range-Based Searchers](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4205r0.html)

`std::search`の`searcher`を受け取るオーバーロードの`range`版を追加する提案。

`std::search`はある範囲内の特定の部分範囲を探索するアルゴリズムです。他のアルゴリズムと同様に検索対象の範囲はと検索したい部分範囲をイテレータペアで受け取り、要素の比較に使用する二項述語をカスタムすることもできます。また、C++20ではRange版が追加されています。

しかし、`std::search`には他のアルゴリズムとは異なるオーバーロードがC++17で追加されており、それが`searcher`オブジェクトを受け取るものです。これは、高性能な専用探索アルゴリズムを利用可能にするためのもので、標準の`searcher`としては`std::boyer_moore_searcher`などが用意されています。

`std::search`はナイーブな実装では2つの範囲の長さ`N, S`に対して`O(NS)`の時間計算量がかかります。専用の検索アルゴリズムでは検索対象のパターンや特性から検索に役立つ情報を事前計算しておくことで事件計算量を改善することができます（ただし、通常その分メモリを必要とします）。例えば`std::boyer_moore_searcher`を用いると最悪の場合の時間計算量を`O(N+S)`まで抑えることができます。

`searcher`オーバーロードは導入されたのがC++17と遅かったため、Boost.RangeやRange-v3などのRangeライブラリの元となったライブラリには含まれておらず、そのためC++20のRangeアルゴリズム導入や現在進行中の数値アルゴリズムの`range`版の作業においてもカバーされていません。

```cpp
std::string haystack = "a quick brown fox jumps over the lazy dog"; // 検索対象範囲
std::string needle = "jump";  // 検索したい部分範囲

// イテレータペアのオーバーロード
std::search(haystack.begin(), haystack.end(), needle.begin(), needle.end()); // ✅ OK
std::ranges::search(haystack, needle); // ✅ OK、C++20から

// 二項述語をカスタムするオーバーロード
std::search(haystack.begin(), haystack.end(), needle.begin(), needle.end(), [](auto a, auto b) { return tolower(a) == b; }); // ✅ OK
std::ranges::search(haystack, needle, [](auto a, auto b) { return tolower(a) == b; });  // ✅ OK、C++20から
std::ranges::search(haystack, needle, {}, [](auto a) { return tolower(a); });           // ✅ OK、C++20から

// 並行アルゴリズム
std::search(std::execution::par_unseq, haystack.begin(), haystack.end(), needle.begin(), needle.end()); // ✅ OK
std::ranges::search(std::execution::par_unseq, haystack, needle); // ✅ OK、C++26から

// searcherを取るオーバーロード
std::boyer_moore_searcher searcher(needle.begin(), needle.end());
std::search(haystack.begin(), haystack.end(), searcher);  // ✅ OK
std::ranges::search(haystack, searcher);          // ❌ Error!
```

この欠落はおそらく意図しないミスだと思われるため、この提案は`std::search`の`searcher`を受け取るオーバーロードの`range`版を追加することを提案するものです。


この提案の変更によって、先ほどのコードで使用できなかった`ranges::search`はそのまま使用可能になります。

```cpp
std::ranges::boyer_moore_searcher searcher(needle); // ✅ OK、こちらもrange対応
std::ranges::search(haystack, searcher);    // ✅ OK
```

また、C++23で追加された`ranges::contains_subrange`アルゴリズムは`std::search`のラッパーであるため、こちらに対しても同様に`searcher`を受け取るオーバーロードを追加することを提案しています。

この提案で追加されるオーバーロードは次のものです

```cpp
namespace std::ranges {
  // search()
  template<forward_iterator I, sentinel_for<I> S, class Searcher, class Proj = identity>
    requires searchable<Searcher, I, S, Proj>
  constexpr auto ranges::search(I first, S last, const Searcher& searcher, Proj proj = {});

  template<forward_range R, class Searcher, class Proj = identity>
      requires searchable<Searcher, iterator_t<R>, sentinel_t<R>, Proj>
  constexpr auto ranges::search(R&& r, const Searcher& searcher, Proj proj = {});

  // contains_subrange()
  template<forward_iterator I, sentinel_for<I> S, class Searcher, class Proj = identity>
      requires searchable<Searcher, I, S, Proj>
  constexpr bool ranges::contains_subrange(I first, S last, const Searcher& searcher, Proj proj = {});
  
  template<forward_range R, class Searcher, class Proj = identity>
      requires searchable<Searcher, iterator_t<R>, sentinel_t<R>, Proj>
  constexpr bool ranges::contains_subrange(R&& r, const Searcher& searcher, Proj proj = {});
}
```

`ranges::search`の戻り値型は`subrange`（イテレータペアを受け取るオーバーロード）または`borrowed_subrange_t`（`range`を受け取るオーバーロード）のどちらかになります。

`std::searchable`は標準の`searcher`の要件を表現するコンセプトで、この提案で追加されるものです。

```cpp
// <iterator>に追加
namespace std {

  template<class Searcher, class I, class S, class P = identity>
  concept searchable =
    copyable<Searcher> &&
    invocable<Searcher, I, S, P> &&
    ranges::forward_range<invoke_result_t<Searcher, I, S, P>>;
}
```

既存の標準`searcher`型`default_searcher`、`boyer_moore_searcher`、`boyer_moore_horspool_searcher`に対しても、`range`版が追加されます。これは、コンストラクタで検索したい部分範囲を取る際に`range`で渡せるようになるほか、検索そのもの（`oprator()`）に対しても`range`を渡せるようになっているものです（なおかつコンセプトによる制約がなされています）。

`rannges::default_searcher`の場合

```cpp
namespace std::ranges {

  template <forward_range R,
            copy_constructible Pred = equal_to,
            indirectly_regular_unary_invocable<iterator_t<R>> Proj = identity>
  class default_searcher {
  public:
    // コンストラクタ
    constexpr default_searcher(iterator_t<R> pat_first, sentinel_t<R> pat_last,
                               Pred pred = {}, Proj proj = {});

    template<typename R2> requires same_as<remove_reference_t<R2>, R>
    constexpr explicit default_searcher(R2&& r);

    template<typename R2> requires same_as<remove_reference_t<R2>, R>
    constexpr default_searcher(R2&& r, Pred pred, Proj proj = {});

    // operator()
    template<forward_iterator I2, sentinel_for<I2> S2, class Proj2 = identity>
      constexpr subrange<I2> operator()(I2 first, S2 last, Proj2 proj2 = {}) const
        requires indirectly_comparable<I2, iterator_t<R>, Pred, Proj2, Proj>;

    template<forward_range R2, class Proj2 = identity>
      constexpr borrowed_subrange_t<R2> operator()(R2&& r2, Proj2 proj2 = {}) const
        requires indirectly_comparable<iterator_t<R2>, iterator_t<R>, Pred, Proj2, Proj>;

    ...
  };
}
```

`{r2, pred, proj2}`で初期化された`searcher`に対して、`ranges::search(rng, searcher, proj)`は内部で`searcher(rng, proj)`を呼び出し、これが`ranges::search(r, r2, pred, proj, proj2)`と等価になる事を意図しています。

### [P4206R0 Revert string support in `std::constant_wrapper`](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4206r0.html)

`std::constant_wrapper`から文字列リテラルのサポートを削除する提案。

当初（P2781R4まで）の`std::constant_wrapper`は次のように定義されていました

```cpp
template <auto X, class = remove_cvref_t<decltype(X)>>
struct constant_wrapper {
    // operators and stuff
};

template <auto X>
constexpr auto cw = constant_wrapper<X>();
```

最終的には（P2781R5から）次のように変更されました

```cpp
template <typename T>
  struct cw-fixed-value; // exposition-only

template <cw-fixed-value X, class = typename decltype(X)::type>
struct constant_wrapper {
    // operators and stuff
};

template <cw-fixed-value X>
constexpr auto cw = constant_wrapper<X>();
```

これは文字列リテラルのサポートのための変更です。`std::cw<"foo">`のように使用すると、文字列リテラル（のポインタ）を定数テンプレートパラメータ（NTTP）として渡すことができないためにエラーになります。P2781R5での変更は`cw-fixed-value<T>`において文字列リテラルを配列でラップすることでこの制限を回避しています。これは他の配列に対しても有効になり、現在の`std::constant_wrapper`は配列サポートを備えています。

しかし、この変更によって`std::constant_wrapper`の使い勝手が損なわれてしまっています。

現在の`std::constant_wrapper`には大きく次の2つの用途のサポートを意図しています

1. 関数呼び出しを横断して定数値を引き渡し、受け取り側がその値を推論して利用できるようにする
    - いわゆる`constexpr`引数の実現
2. 操作（主に演算子）が定数性を維持するドメインとして機能させる
    - 例えば、`std::cw<5> + std::cw<3>`は8ではなく`std::cw<8>`

問題になるのは1の用途においてです。その場合の典型的な使用方法は次のようになります

```cpp
template <int I>
auto f(std::constant_wrapper<I>) -> void {
  // ...
}

auto main() -> int {
  f(std::cw<5>);
}
```

P2781R4まではこのコードは機能しますが、P2781R5からは機能しません。なぜなら、`std::cw<5>`は`std::cw<cw-fixed-value<int>(5)>`になっているため、`std::constant_wrapper<int(I)>`にマッチしないためです。

回避するためには次のように定数テンプレートパラメータを`auto`で受けるようにします

```cpp
template <auto I>
auto f(std::constant_wrapper<I>) -> void {
  // ...
}
```

しかし、`I`は`int`ではなく`cw-fixed-value<int>`型であり、説明専用型であるうえに`int`への暗黙変換も定義されていません。そのため、今度は利用側（関数内）で定数値をそのまま取り出せなくなります。

```cpp
template <auto I>
auto f(std::constant_wrapper<I> c) -> void {
  constexpr int A = I;                // error
  constexpr int B = std::cw<I>.value; // ok
  constexpr int C = c.value;          // ok
  constexpr int D = c;                // ok、constant_wrapper自体は暗黙変換をサポートしている
}
```

これを受け入れたとしても、最初のコードのように定数引数を取りたい場合にその引数型を具体的な一つに指定することは自然なユースケースです。現在の`constant_wrapper`でそれを実現する最も簡単な方法は2つ目のテンプレートパラメータを利用することです

```cpp
template <auto I>
auto f(std::constant_wrapper<I, int>) -> void {
  // ...
}

auto main() -> int {
  f(std::cw<1>);  // ok
  f(std::cw<2u>); // error
}
```

`constant_wrapper<V, T>`の2つ目のテンプレートパラメータは`V`の元の値の型を指定することで`V`の型に対するADLを機能させるためのものです。これは本来ユーザーが指定したり使用するものではないはずのものです。

その他にもいくつかの問題が指摘されています

- 2つ目のテンプレートパラメータで型が繰り返されることでマングル名が肥大化する
- 定数テンプレートパラメータと`constant_wrapper<V, T>`の値のアドレスが一致しなくなる
    - 定数テンプレート引数`I`と対応する`cw.value`のアドレスが異なる

このように、P2781R5でのクラス構造の変更は`constant_wrapper`のユーザビリティを損ねているため、この提案ではP2781R5での変更をrevertしてP2781R4のクラス構造に戻すことを提案しています。また、これはC++26へのDRとして提案されています。

この変更によって`std::cw<"foo">`の様な文字列リテラル（および配列）サポートは無くなってしまいますが、その点についてこの提案ではそもそも取れるだけで利用がほとんどできない事を指摘しています。

```cpp
// 比較できない
auto a = std::cw<"foo">;
auto b = std::cw<"bar">;
a == b; // error

// 非リテラルの文字列を取れない
constexpr char const* msg = "amount";
auto c = std::cw<msg>; // error

// 受け取り側では文字列リテラルであることを確認したうえでstring_viewに入れないと利用できない
template <auto V, size_t N>
auto f(std::constant_wrapper<V, char const[N]>) -> void {
  constexpr auto S = std::string_view(std::cw<V>.value);
}

auto main() -> int {
  f(std::cw<"amount">);
}
```

`constant_wrapper`が文字列リテラルを特別扱いする必要があるのは、文字列と定数テンプレートパラメータの相性が悪いという言語側の問題があるためです。例えば、文字列リテラルが定数テンプレートパラメータとして扱えないことや、`std::string_view`/`std::string`が定数テンプレートパラメータとして扱えないことなどです。言語の問題をライブラリで解決しようとした代償として上記のような問題が発生しており、なおかつこの問題は言語側で解決策が導入された後でも永続的に残り続けます。

現時点でもこの問題を解消しようとする言語側の提案はいくつか提出されています（P0242R2, P3380R1）。

また、この提案の変更後でも`fixed_string<N>`のようなものを使用すれば文字列リテラルを`constant_wrapper`で使用することはでき、その場合は利用側でも今の文字列リテラルサポートよりも使いやすくなります（ユーザーがそのような型を用意しなければならない点が問題なだけ）。

この提案は2026年6月の全体会議で承認され、C++26に適用されています。

### [P4209R0 `numeric_limits` for `std::simd`](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4209r0.html)

`simd::basic_vec`に対する`std::numeric_limits`の特殊化を追加する提案。

C++26の`std::simd`は型`T`の並列拡張版の型であるデータ並列型`std::simd::basic_vec<T, Abi>`を導入するもので、`simd::basic_vec<T>`は`T`とほとんど同じ操作が行えるようになっていることで`simd::basic_vec<T>`と`T`で同じ数値計算処理を行うコードを共通化することができます。

そのような計算コードでは往々にして`std::numeric_limits<T>`が参照されます。

```cpp
template <class V>
bool nearly_equal(V a, V b) {
  return std::abs(a - b) <=
         std::numeric_limits<V>::epsilon() * std::max(std::abs(a), std::abs(b));
}
```

`simd::basic_vec<T>`には`std::numeric_limits`の特殊化が提供されていないため、`std::numeric_limits`のメンバ関数等を利用することができません。このような場合、`std::numeric_limits<typename V::value_type>` （スカラ型では動作しない）とするか、`simd::basic_vec<T>`で利用可能にすることを諦めるかのいずれかを選択せざるを得ません。

同じことは`epsilon()`だけではなく`is_iec559, is_signed, is_integer`などの他の関数でも問題になりえます。また、`std::midpoint, std::lerp, std::hypot`や`<random>`などの`std::numeric_limits`を使用する機能について`simd::basic_vec<T>`対応を考える際にも問題となります。

この提案は、`simd::basic_vec<T>`でも利用可能な汎用的数値計算コードの記述を促進するために、`simd::basic_vec<T>`に対して`std::numeric_limits`の特殊化を提供するようにする提案です。

提案する`numeric_limits<basic_vec<T, Abi>>`は`basic_vec<T, Abi>`の型モデルを記述するものであり、その型モデルは`T`の型モデルを要素ごとに適用したものとしています。

`std::numeric_limits`のメンバは大きく2種類にカテゴリ分けされます

1. 特性メンバ
    - 型の性質（）を表すbool型や整数型、列挙型などを返す静的データメンバ
    - `digits, is_signed, radix, is_iec559, round_style`など
2. 値を返すメンバ
    - 型`T`の値を返す静的メンバ関数
    - `min(), max(), lowest(), epsilon(), infinity(), quiet_NaN()`など

`basic_vec<T, Abi>`の特殊化の場合はそれぞれ

- 特性メンバは、対応する`std::numeric_limits<T>`と同じ値を持つ
    - 要素ごとの型モデルを記述する
- 値を返すメンバは、`basic_vec<T, Abi>`のブロードキャストコンストラクタを用いてブロードキャストされた結果の各要素が、対応する`std::numeric_limits<T>`での値と等しくなる`basic_vec<T, Abi>`オブジェクトを返す

となります。

提案より、実装例

```cpp
#include <limits>
#include <simd>

namespace std {

template <class T, class Abi>
  requires std::numeric_limits<T>::is_specialized
struct numeric_limits<std::simd::basic_vec<T, Abi>> {
private:
    using V = std::simd::basic_vec<T, Abi>;
    using S = numeric_limits<T>;

public:
    static constexpr bool is_specialized = true;

    // Value-returning members: broadcast the scalar limit.
    static constexpr V min()           noexcept { return V(S::min()); }
    static constexpr V max()           noexcept { return V(S::max()); }
    static constexpr V lowest()        noexcept { return V(S::lowest()); }
    static constexpr V epsilon()       noexcept { return V(S::epsilon()); }
    static constexpr V round_error()   noexcept { return V(S::round_error()); }
    static constexpr V infinity()      noexcept { return V(S::infinity()); }
    static constexpr V quiet_NaN()     noexcept { return V(S::quiet_NaN()); }
    static constexpr V signaling_NaN() noexcept { return V(S::signaling_NaN()); }
    static constexpr V denorm_min()    noexcept { return V(S::denorm_min()); }

    // Trait members: forward unchanged from numeric_limits<T>.
    static constexpr int  digits         = S::digits;
    static constexpr int  digits10       = S::digits10;
    static constexpr int  max_digits10   = S::max_digits10;
    static constexpr bool is_signed      = S::is_signed;
    static constexpr bool is_integer     = S::is_integer;
    static constexpr bool is_exact       = S::is_exact;
    static constexpr int  radix          = S::radix;
    static constexpr int  min_exponent   = S::min_exponent;
    static constexpr int  min_exponent10 = S::min_exponent10;
    static constexpr int  max_exponent   = S::max_exponent;
    static constexpr int  max_exponent10 = S::max_exponent10;

    static constexpr bool has_infinity      = S::has_infinity;
    static constexpr bool has_quiet_NaN     = S::has_quiet_NaN;
    static constexpr bool has_signaling_NaN = S::has_signaling_NaN;

    static constexpr bool is_iec559  = S::is_iec559;
    static constexpr bool is_bounded = S::is_bounded;
    static constexpr bool is_modulo  = S::is_modulo;

    static constexpr bool              traps           = S::traps;
    static constexpr bool              tinyness_before = S::tinyness_before;
    static constexpr float_round_style round_style     = S::round_style;
};

} // namespace std
```

### [P4211R0 Adaptors For Closed Ranges](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4211r0.html)

閉区間を半開区間に変換するRangeアダプタの提案。

C++のイテレータは範囲を半開区間（`[begin, end)`）としてモデル化しており、イテレータおよび`range`を扱うライブラリ機能のほとんどのものもこのことを仮定して設計・実装されています。

しかし、イテレータ範囲による閉区間の抽象化が必要になる場合も依然として存在しています。例えば、`views::iota(INT_MAX - 20, INT_MAX)`は`INT_MAX - 1`までの数値しか生成しませんが、符号付整数型のオーバフローが未定義動作であることによって、`INT_MAX`（あるいは一般の値型で表現可能な最大値）を含む`views::iota`を得ることができません。

このような理由によってRangeライブラリが閉区間をうまく扱えないことによる問題はP2406R5で以前に報告されていました。

```cpp
auto iss = std::istringstream("0 1 2");

for (auto i : views::istream<int>(iss) | views::take(1)) {
  std::cout << i << '\n'; // 0だけが消費されるはず
}

auto i = 0;
iss >> i;
assert(i == 1); // FAILS, i == 2、どこかで1が消費されている
```

`input_iterator`に対する`views::take`は`std::counted_iterator`をラップした範囲を返します。アダプタの合成段階では何もせず、`begin()`によるイテレータ取得段階で`views::istream`のイテレータによってストリームから値が取得されます。`for`ループ開始時点ではストリームは`1`を指し、イテレータ（ループ変数`i`の値）は`0`を指しています。

ループが1周すると、終了判定のために`std::counted_iterator`が1つ進められ、それによって`views::istream`のイテレータの進行においてストリームから値が取得されます。この後イテレータの終端チェックで`std::counted_iterator`の`it == end`が`true`を返す（内部カウンタが1 -> 0に到達するため）ことで`for`ループは終了します。

`for`ループ終了直前では、ストリームは`2`を指し、イテレータは`1`を指しています。

`for`ループ終了に伴って`views::istream<int>(iss)`のviewおよびイテレータは破棄されるため、ストリームから消費された`1`は消えてなくなります。

そのため、その後ストリームを読み出すと想定よりも1つ進んだ`2`を返します。

これは`views::istream`や`views::take`に`std::counted_iterator`、あるいは範囲`for`までも、あらゆるものがイテレータ範囲操作を半開区間だとして扱うために起きています。なぜなら、範囲を表現するために2つのイテレータ値が必要となるため、それを作り出すために大本の入力（`iss`）から余分に一つ分要素が消費されてしまうからです。

P2406R5ではこの問題の解決のために、内部カウンタがすでに0に到達している場合に基底イテレータのインクリメントを行わない`std::lazy_counted_iterator`の導入と、それを`views::take`で使用するようにする（こちらは破壊的変更）ことを提案していました。しかしこの提案は破壊的変更のための設計がC++23に間に合わなかったことによって結果的にリジェクトされています。

その後、P2709R0によってP2406R5が解決しようとした本質的な問題はC++のイテレータモデルでは閉区間を扱えないことにあるということが説明されました。

この提案はそれらの流れを受けて、閉区間を表すイテレータ範囲を通常のイテレータモデル（半開区間）で扱えるようにしようとするものです。

この提案はP2406R5の内容ををベースにその適用範囲を拡大したもので、次のような変更を含んでいます

- `count == 0`（内部カウンタが終端に到達している）の場合に基底イテレータを進行させない`std::lazy_counted_iterator`（`views::lazy_counted`）
- ランダムアクセス可能な場合に基底イテレータとして`std::lazy_counted_iterator`を使用する`views::lazy_take`アダプタ
- あらゆる種類の閉区間（`it == end`であっても`*it`が有効であるような範囲）を対象とした汎用アダプタ`views::as_closed`
- 整数の閉区間範囲を生成する`views::closed_iota`ファクトリ
    - `views::closed_iota(a, b)`は`views::as_closed(views::iota(a, b))`であり、`[a, b]`の範囲を表す

```cpp
std::vector vec{1, 2, 3, 4, 5};
views::as_closed(vec.begin() + 2, vec.begin() + 4); // [3, 4, 5]
```
```cpp
for (int i : views::closed_iota(0, 5)) {
  std::cout << i << ' '; // 0 1 2 3 4 5
}
```

`views::as_closed`は`views::as_closed(rng)`、あるいは`views::as_closed(start, end)`の様に範囲を受け取って、その（イテレータ）範囲を閉区間の範囲（`end`に対応する部分まで値が有効な範囲）に変換するRangeアダプタです。

閉区間を半開区間として扱うには、終了判定をごまかす（必要以上にインクリメントしない）ためのオーバーヘッドが必要となります。この提案ではそれを受け入れたうえで、`as_closed_view`のイテレータが終端判定のための`bool`値を一つ保持して、イテレータが終端に到達しているときにそのことをこの`bool`値に記録してインクリメントを回避します。

```cpp
// `as_closed_view`のイテレータの実装概要
struct as_closed_view<I, S>::iterator {
  I current;
  S last;
  bool past_the_end;

  iterator& operator++() {
    if (current == last) {
      past_the_end = true;
    } else {
      ++current;
    }
    return *this;
  }
  
  constexpr decltype(auto) operator*() const { return *current_; }
};
```

終了判定でもこの`past_the_end == true`であるかを追加でチェックすることで、`current == last`に到達した時でもすぐに終端扱いせず、1進行分終端判定を遅らせます。

`std::lazy_counted_iterator`の場合は内部カウンタが`0`に到達してるか否かを代わりに使用できるので追加の`bool`値は不要です。

P2405R5で報告されていた、`views::filter`が閉区間を作り出してしまい無限ループに陥る例

```cpp
// C++20（26でも
for (auto i : views::iota(0)
        | views::filter([](auto i) { return i < 11; })
        | views::take(11))
    std::cout << i << '\n'; // Infinite loop!

// この提案1
for (auto i : views::iota(0)
        | views::filter([](auto i) { return i < 11; })
        | views::lazy_take(11))
    std::cout << i << '\n'; // OK

// この提案2
for (auto i : views::iota(0)
        | views::filter([](auto i) { return i < 11; })
        | views::take(10) | views::as_closed)
    std::cout << i << '\n'; // Also OK
```

### [P4212R0 ISO/IEC 60559 Floating-Point Support Annex for C++](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4212r0.pdf)

ISO/IEC 60559:2020に準拠する浮動小数点数演算のサポートに関するAnnexを追加する提案。

C++の主だった実装のほとんどはISO/IEC 60559:2020（IEEE754）の浮動小数点数をサポートするハードウェアを対象にしています。ただし、C++が規格としてサポートしているのはIEEE754の定義する浮動小数点数形式に従う浮動小数点数データ型（`double`/`std::float64_t`など）とそれを用いた最低限の演算のみで、ISO/IEC 60559規格の定める浮動小数点数演算セマンティクスを完全にはサポートしていません。

このことによってC++環境での浮動小数点数演算の移植性や再現性は担保されず、それを得ようとすることを著しく困難にしています。

この提案は、C++規格に準拠したうえでISO/IEC 60559:2020の浮動小数点数演算もサポートできるようにするために、ISO/IEC 60559:2020のC++適合についてを規定した文書をC++規格のNormative Annexとして追加することを目指すものです。

同様のものはC言語規格においてはAnnex Fとしてすでに定義されています。しかしそれはあくまでC向けであり、C++では型システムやテンプレート、定数式など言語セマンティクスに加えて標準ライブラリの構造も異なるため、C Annex FをC++に持ってくるのではなく、C++において独自にISO/IEC 60559:2020への適合要件を定めようとしています。

そのためにはISO/IEC 60559:2020規格の3項から11項の部分について検討が必要であり、提案ではこれらの各項ごとにそのサポートのためにC++実装側でどのような作業や変更が必要となるかをまとめています。

この提案の目的は、C++規格に準拠した処理系においてさらにISO/IEC 60559:2020に準拠するために必要な適合要件についてを規格の外側のAnnexで規定しておこうとするもので、C++規格内の浮動小数点数演算をISO/IEC 60559:2020準拠のものにしようとするものではありません。そうした活動は別に行われており、この提案はそのために必要な作業やギャップを明らかにするものでもあります。

### [P4214R0 Composable Correctness and Progress Guarantees](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4214r0.html)

C++の並行処理プリミティブについて、合成可能な進捗保証（progress guarantees）を提供すべきとする文書。

プログラムの正しさを推論するために、Leslie Lamportは安全性（Safety）と活性（Liveness）という2つの性質に着目した分類方法を提案しました。Lamportの言う安全性とは「ある事象が決して起こらないこと」を主張するもので、例えばプログラムの部分正当性（partial correctness）は安全性の一種です。これは、「正しい入力でプログラムが開始された場合、正しい出力が生成されない限りプログラムは停止しない」ことを主張するものです。あるいは、「悪いことが起こらない事」と定義されます。

一方、活性とは「ある事象が必ず起こること」を主張するもので、例えば「正しい入力で開始されたプログラムは終了する」という主張があります。あるいは、「良いことが最終的に起こる事」と定義されます。

そして、安全性と活性が同時に満たされているプログラムの事を正しいプログラムと定義します。

Lamportのこの定義に従うと、安全性とはプログラムの正しさの一部であり、安全性はプログラムの正しさと対立するものではありません。安全性を向上させることができるならば、プログラムの正しさも向上させることができます。

また、プログラムの部分正当性は安全性の一部です。部分正当性は「プログラムが答えを生成する場合、その答えは正しいものである」という性質を指していますが、これは「プログラムがいずれ答えを生成する」（停止性）ことまでは主張していません。この部分正当性に欠けている停止性の部分が終了（termination）あるいは進捗（progress）です。

これらの概念から、プログラムの正しさ（全正当性）は次のように表せます

全正当性（Total correctness） = 部分正当性 + 終了

すなわち、部分正当性=安全性、終了（進捗）=活性であり、安全性と活性の両方が保証されているプログラムは正しい（プログラムはいずれ答えを生成し、その答えは正しいものである）ものです。

プログラムの部分正当性は不変条件によって定義可能です（この文書ではそう仮定します）。プログラムの不変条件が破られているとき、それはそのプログラムの安全性に関する特性が侵害されていることを表しています。すなわち、安全性の侵害は実行途中の各段階において検出可能です。

プログラムが完了し、不変条件が一度も破られていない場合、そのプログラムは安全である（に実行され完了した）といえます。一方、その実行の途中で不変条件の違反が検出された場合、その後に実行されるプログラムは安全ではありません。

このことは、安全性は合成可能であることを表しています。Aがその事前条件を満たし不変条件を破ることなく完了し、（Aの実行とは独立して）Bも同様に事前条件も不変条件も破ることなく完了する場合、AとBを続けて実行してもそれらの不変条件が破られることはありません。ただし、ここでのそれぞれ不変条件には双方の事前条件が維持されることが暗黙に課されます。AはBの事前条件や不変条件を無効にしてはならず、BはAの実行後もAの正しさのために必要な不変条件を無効にしてはなりません。

不変条件に着目することで、安全性が局所的、構造的かつ合成可能であると言えます。

一方、活性は安全性とは異なる特性を持ちます。まず、活性の侵害は実行の各段階で有限時間でそれを証明できません。

Aの実行が完了するものであり、Bの実行も完了するものであるとしても、AとBを組み合わせた場合にも完了するとは限りません。例えば、食事する哲学者の問題がこの典型的な例です。

このように、一般に活性は合成可能ではありません。

前述のように、プログラムの正しさは安全性と活性の双方によって評価されます。その評価順序は任意ですが、まず安全性を確認しておくことで活性に関する推論を簡略化することができます。活性の証明は「答えが生成され、それが正しいこと」を示すことですが、安全性（「答えが生成されるならば、それは正しい」）が満たされていれば「答えが生成されること」だけを示せばよいためです。

すなわち、安全性が満たされていれば活性の証明は進捗（progress）の証明へと帰着します。

活性を進捗に言い換えても、依然として活性は一般に合成可能ではありません。しかし、進捗が局所的に合成可能であることが分かっていれば、安全性の保証の上で活性に関する保証もまた合成可能となります。これにより、安全性が成立し、進捗が合成可能であれば、正当性も合成可能となります。

複数の構成要素からなり進捗特性が合成可能であることが示されるシステムにおいて、以下の条件を満たすことで正当性を合成的に確立できます

- 各部品が部分的に正当である（安全性）
- 各部品はスケジューリングされ実行された際に進捗する（局所的な停止性）
- 最終的に観測可能な結果を生成可能なコンポーネントが、いずれスケジューリングされる

この文書はこのような論理背景の下で、優れたソフトウェアエンジニアは次の事を目指すべきとします

- プログラムのあらゆる部分において安全性（部分正当性）を確保すること
- 進捗（progress）の特性が合成可能な機能のみを使用すること

そして、C++標準化委員会はC++プログラマのこのような努力を支援するために、次のような取り組みを行うべきとしています

- 未定義動作を最小限に抑えること
    - 新しいライブラリにおける未定義動作の発生個所を減らし、そのような状態に陥りにくくする
- 安全な機能の提供に努めるとともに、新機能の提案時には安全性に関する議論を行うこと
- 進捗の保証が不可能なコンポーネントの標準化を回避すること
    - ただし、リスクが明確に理解されており、利益がそのリスクを明らかに上回る場合はこの限りではない

これは、SG1向けに、特に並行処理のプリミティブの新規機能の目指すべき方向性についての設計指針を提示するもので、具体的に提案したりするものではありません。

SG1のレビューでは、この方向性に賛同し、この文書の内容を念頭に置くことは有用としつつも、SG1としての正式な方針を策定することはない、としています。

### [P4216R0 Comparisons for span](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4216r0.pdf)

`std::span`に比較演算子を追加する提案。

C++にはデータの非所有参照を表す型がいくつかあり、`std::span`もそのうちの一つです。しかし、その中で`std::span`のみが比較演算子（`==` `<=>`）をサポートしていません。この提案は、この非一貫性を解消しようとするものです。

```cpp
std::reference_wrapper<int> r0 = ..., r1 = ...; 
std::optional<int&> o0 = ..., o1 = ...; 
std::string_view s0 = ..., s1 = ...; 
std::span<T> p0 = ..., p1 ...;

// 同値比較
// 全て深い比較（参照先の値の比較）を行う
r0 == r1; 
o0 == o1; 
s0 == s1; 

p0 == p1; // ng
ranges::equal(p0, p1);  // ok

// 三方比較
// 全て深い比較（参照先の値の比較）を行う
r0 <=> r1; 
o0 <=> o1; 
s0 <=> s1; 

p0 <=> p1; // ng
lexicographical_compare_three_way( 
  p0.begin(), p0.end(), 
  p1.begin(), p1.end(), 
  synth-three-way  // 説明専用であるため使用できない
);
```

`std::span`の元の提案でも当初は比較演算子が定義されていましたが、途中で削除（P1085によって）されました。`std::span`の参照性に関する次のような理由によるようです

- `std::span`は参照セマンティクスを持つため、その値が等価的に変化しうる
- `std::span`は深い`const`性を強制しない
- `std::span`は代入時にリバインド（参照の再束縛）される

しかし、2つ目の点以外は`std::string_view`にも当てはまっている（`std::string_view`は比較演算子を提供している）ほか、比較機能を削除してもこれらの点が何か緩和されるわけではありません。

そして、`std::optional<T&>`に関する議論の中で、これらの点は参照型のセマンティクスとしては適切なものであることがすでに確立されています（特に、代入時のリバインドが正しい挙動であるという結論に至ったのはごく最近）。

これらの理由から、以前の懸念は比較演算子を提供する理由にならないとして、この提案では`std::span`にも比較演算子を定義するようにしています。

ここで提案されている比較演算子は、`std::string_view`などと同様に深い比較（参照の比較ではなく、要素ごとの比較）とすることが提案されています。

```cpp
std::span<T> p0 = ..., p1 ...;

p0 == p1;   // ok
p0 <=> p1;  // ok
```
```cpp
std::vetor vec = {1, 2, 3, 4};
std::array arr = {1, 2, 3, 4};

std::span sp0{vec};
std::span sp1{arr};

contract_assert(vec == arr);  // ✅、要素毎の比較になる
```

### [P4217R0 `when_all()` is just `just()`](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4217r0.pdf)

`execution::when_all()`のゼロ引数の呼び出しを可能にする提案。

`execution::when_all()`は任意個数の`sender`を受けて、すべての`sender`が完了した時に完了する`sender`を返す`sender`アルゴリズムです。複数の非同期処理の合流地点のような働きをします。

`execution::when_all()`のゼロ引数の呼び出しはその制約（`sizeof...(sndrs) != 0`）によって禁止されているため、`execution::when_all()`の様な呼び出しはコンパイルエラーになります。

```cpp
// senderで記述されたなにか非同期処理
execution::sender auto sndr1 = ...;
execution::sender auto sndr2 = ...;
execution::sender auto sndr3 = ...;

// when_all()による合流
execution::sender auto when_all_sndr = execution::when_all(sndr1, sndr2, sndr3);  // ok
// when_all_sndrをconnectしてstartすると、sndr1~3の全ての完了を待機してから完了する操作を実行する

execution::when_all();  // ng、引数無しでの呼び出しはできない
```

この提案は、その制約を変更して`execution::when_all()`のような引数無しの呼び出しを許可し、その`sender`の動作を無条件完了するものにする提案です。これは、`execution::just()`と同じ動作になります。

```cpp
execution::sender auto when_all_sndr = execution::when_all();  // ok
// when_all_sndrをconnectしてstartすると、即座に完了する操作を実行する

execution::sender auto just_sndr = execution::just(); // ok（この提案以前から
// just_sndrをconnectしてstartすると、即座に完了する操作を実行する
```

`execution::when_all()`の様な呼び出しが禁止されていることは、`sender`を用いたジェネリックな（例えば可変長引数）処理を記述する際に不必要な例外処理（引数が1以上であることを確認するなど）を行う必要性を生じさせるなど不便をもたらします。似ているイテレータアルゴリズムである`std::all_of`が空の入力に対して`true`を返すように、`execution::when_all()`は自明に完了させればよく禁止する理由はない、としています。

### [P4220R0 Design goals for `zstring_view`](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4220r0.html)

`std::zstring_view`の設計目標を明確化する提案。

P3655R4ではnull終端された文字列を表す`std::string_view`として`std::cstring_view`（`std::zstring_view`）が提案されています。この提案では、P3655R4に対してその設計目標が明らかではないとして、明確化を求めるとともに`std::zstring_view`に対する論点を整理するものです。

この提案では、`std::zstring_view`/`std::cstring_view`という文字列型の要望が多くともそれらの要望が同じ型を想定しているとは限らないことと、異なる目的の間にあるトレードオフを指摘し、設計目標が曖昧なまま標準化を進めてしまうと議論に参加する関係者の間ですら設計目標が一致せず、結果として誰のニーズも満たさないものになってしまうと警告しています。

この提案ではまず、C文字列の規約を次のように整理しています

- 型は`const char*`
- ポインタはnullではない
- ポインタは有効な文字列配列を指している
- 配列を走査すると、未定義動作に陥ることなくnull文字に到達することが保証される
    - 文字列サイズはnull文字の位置によって決まる
- ゼロサイズ文字列も有効な文字列の値として認められる

これはC言語およびCのライブラリにおいて文字列を表現する際の慣習です。

P3655R4で示されている動機は次のようなものです

- 関数の作成者がPOSIXの`open()`のような関数を呼び出そうとしている
- その作成者が関数の引数型として`const char*`ではなく`std::string_view`を使用することにこだわっている

このような場合において`std::string_view`がnull終端を感知しないために、「文字列がnull終端されている」という事前条件を表明する文字列型が求められています。

結果的に内部ではC文字列の規約による`const char*`を扱うにもかかわらず、`const char*`ではなく新しい型が必要とされる理由は次のようなものが考えられます。

1. C文字列の規約を型に反映させるため 
    - たとえ中身が単なる`const char*`だったとしても、型名でC文字列の規約に従うことを明示する
2. その型を通じて、C文字列の規約を実行時に強制できるようにするため
3. `const char*`に対する`operator==`がもつ誤解を招きやすいセマンティクスを回避するため
4. C文字列の規約に従いつつ、文字列の長さを明示的に保持する型を提供するため

4の目的が達成された場合は文字列の長さが必要になる処理を効率化できる可能性がありますが、その一方でPOSIXの`open()`のような関数はこちらがその長さを知っているかどうかとは無関係に文字列の長さを計算してしまうため、二重のオーバーヘッドになる可能性があります。

```cpp
zstring_view zs = get_c_string(); // 𝒪(n) pass
open(zs.data());          // another 𝒪(n) pass
```

提案では、これらの分析を元に2つの設計目標を挙げています

1. C文字列の規約の実行時検証
    - C文字列としての規約を実行時に検証する機能を備えた`const char*` 
2. C文字列 + サイズ情報の事前計算
    - 長さ情報を内部に保持する
    - null終端を仮定する`std::string_view`

これらの設計目標にはそれぞれトレードオフがあります

1. C文字列の規約の実行時検証
    - `const char*`からの構築を許すとnull終端を保証できない
        - `zstring_view(const char*)`の様なコンストラクタ
2. C文字列 + サイズ情報の事前計算
    - コンストラクタで長さを事前計算しても最終的に渡すCライブラリAPIでは再計算される
        - 二重の操作コストがかかる
    - 文字列途中にnull文字が入った場合にC文字列の規約の長さとの不整合が起こる

これらの目標（およびここから要件を緩和した派生目標）においてどのようなコンストラクタ（ファクトリ関数）を提供するか、どのようなインターフェースを提供するか（`std::string`に準ずる豊富なインターフェースを提供すべきか）は、設計目標をどこに置くかにかかっています。

いずれの目標を定めても受け入れる必要のあるオーバーヘッドが存在し、すべての目標を同時に目指すことはできません。現在のP3655R4では目標が明確ではなく、コンストラクタやインターフェースの採用に合理性が無いため、どこを目標にするのか明確にしてからでなければLEWGは提案を承認するべきではないとしています。
