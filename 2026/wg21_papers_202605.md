### [P4036R0 Info: Why Span Is Not Enough](https://www.open-std.org/jtc1/sc22/wg21/docs/papers/2026/p4036r0.pdf)

I/Oの観点から、バイト列を表現するベストな型を考察する文書。

バイトシーケンスを表す型としては`std::span<std::byte>`が一番に上がりますが、この文書ではI/O処理においてはそれだと使いづらい面があり、専用のバッファ型が必要になる事を説明しています。

`span<byte>`では不十分な理由は、プラットフォームで定義されるI/O操作が多くの場合1つのバイトバッファ（領域）を取るのではなくバイト領域の配列を取るようになっているためです。これにより、`span<byte>`はI/Oのためのバッファを表現するのに不十分となります。

`span<span<byte>>`ならばバッファ配列を表現することができます。しかし、バッファそのもの（`span<byte>`）はどこかに実体を持ちそれを借用するだけだったとしても、そのビューの配列（`span<span<byte>>`）が必ずしもそうであるとは限りません。バッファ配列そのものの所有権はどこか別の場所にあるものではなく、そうしないと関数の呼び出し境界で`span<span<byte>>`を返す事で容易にダングリングしてしまいます。

```cpp
class message {
  span<span<byte>> buffers_; // borrows... what?
};

span<span<byte>> prepare_message(span<byte> hdr, span<byte> body) {
  span<byte> bufs[] = { hdr, body };
  return { bufs }; // dangling
}

void start_send(socket& s, span<byte> hdr, span<byte> body) {
  span<byte> bufs[] = { hdr, body };
  s.async_send(span<span<byte>>(bufs), callback);
  // returns immediately; bufs destroyed; dangling
}
```

`vector<span<byte>>`のように`span<byte>`の`range`にすればこの問題を解消することができます。この場合は、バッファ配列全体を1つのバッファとして扱ってバッファの消費を表現することができません。`vector<span<byte>>`に対してRangeアダプタを適用しても、バッファ単位の操作になりバイト要素単位ではありません。バッファ配列という構造を維持したままバッファの消費という操作を行う方法が無いため、この表現は適していません（`views::join`はバッファ配列という構造が維持されないので選択肢に上がらない）。

そのような操作が追加されたとしても、`std::span<byte>`がすでにバイト配列のビューとして使用されすぎているために、I/O専用のバッファ操作アルゴリズム（Rangeアダプタ）は`std::span<byte>`によって表現されているものがI/Oバッファなのかそれ以外のもの（シリアライズ・暗号化・ハッシュ・メモリマップなど）を区別できません。これにより、I/Oバッファ専用のデバッグなどを組み込むことが難しくなり、安全性が損なわれます（`BOOST_ASIO_ENABLE_BUFFER_DEBUGGING`のようなもの）。

この文書では、Boost.Asioの`mutable_buffer`（書き込み可能バッファ）/`const_buffer`（読み込み専用バッファ）がI/Oのためのバッファとして適しているとしています。

```cpp
class mutable_buffer {
  unsigned char* p_ = nullptr;
  std::size_t n_ = 0;
public:
  mutable_buffer() = default;
  mutable_buffer(mutable_buffer const&) = default;
  mutable_buffer& operator=(mutable_buffer const&) = default;
  constexpr mutable_buffer(void* data, std::size_t size) noexcept
      : p_(static_cast<unsigned char*>(data)), n_(size) { }
  constexpr void* data() const noexcept { return p_; }
  constexpr std::size_t size() const noexcept { return n_; }
  constexpr mutable_buffer& operator+=(std::size_t n) noexcept
      { p_ += n; n_ -= n; return *this; }
};

class const_buffer {
  unsigned char const* p_ = nullptr;
  std::size_t n_ = 0;
public:
  const_buffer() = default;
  const_buffer(const_buffer const&) = default;
  const_buffer& operator=(const_buffer const& other) = default;
  constexpr const_buffer(void const* data, std::size_t size) noexcept
      : p_(static_cast<unsigned char const*>(data)), n_(size) { }
  constexpr const_buffer(mutable_buffer const& b) noexcept
      : p_(static_cast<unsigned char const*>(b.data())), n_(b.size()) { }
  constexpr void const* data() const noexcept { return p_; }
  constexpr std::size_t size() const noexcept { return n_; }
};
```

これはNetoworking TSにすでにあるものです。

これらは`span<byte>`に対応するバッファ型であり、バッファ配列型ではありません。バッファ配列型はこれらの`range`（`vector<mutable_buffer>`など）で表現するようにしています。`mutable_buffer`が要素単位の操作をサポートしていることと、バッファ型が`span<byte>`ではないことでI/Oバッファ配列専用のアルゴリズムを提供可能になり、前述の問題が解消されるためです。
